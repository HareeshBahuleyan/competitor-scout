# Database migrations

Alembic owns the ordered history of the Competitor Scout PostgreSQL schema.
Migration files live in `versions/` and use this naming convention:

```text
NNNN_<operation>_<subject>.py
```

Examples include `0002_create_competitor_and_source_tables.py`,
`0006_add_user_defaults_and_nullable_request_ids.py`, and
`0007_remove_invite_allowlist.py`. Alembic identifies a migration by the
`revision` value inside the file, not by its filename.

## Common commands

Run commands from `apps/backend`:

```bash
# Apply all pending migrations
uv run alembic upgrade head

# Show the current and available revisions
uv run alembic current
uv run alembic history

# Verify that SQLAlchemy metadata has no uncommitted schema drift
uv run alembic check

# Generate a candidate migration for a model change
uv run alembic revision --autogenerate -m "add finding status"

# Exercise the latest downgrade and restore it
uv run alembic downgrade -1
uv run alembic upgrade head
```

The local Docker `prestart` service runs `alembic upgrade head` before
`backend-api` and `scout-worker` start.

## Migration policy

- Keep migrations in one chronological sequence rather than domain subdirectories.
- Give each migration one coherent schema or data-change purpose.
- Review autogenerated operations, constraint names, indexes, defaults, and nullability.
- Import Alembic and SQLAlchemy primitives, not application ORM models.
- Provide a safe downgrade when practical. Document irreversible or destructive behavior.
  Migration `0007` drops the invite allowlist and its rows; its downgrade recreates
  the table structure, not the deleted data.
- Test upgrades against PostgreSQL; do not rely on SQLite behavior.
- Never edit or reorder a revision after it has reached a shared or Railway environment.
  Add a new corrective migration instead.
